Column Store Architecture (OLAP + OLTP)

Tables: ACDOCA, BSEG, VBAP, MATDOC
Dual-Buffer Model
1. RAM Dual-Storage Engine: Main + Delta

Column Store relies on two memory buffers:
• Main Storage: Heavily compressed (dictionary encoding, prefix coding, run-length), sorted, and read-optimized. Highly expensive to write in-place.
• Delta Storage: Lightly compressed, write-optimized buffer that receives all transactional INSERT, UPDATE, and DELETE operations immediately.

2. Persistence to `/hana/data`

• During a Savepoint, dirty pages from both Delta and Main storage are flushed to the data volume using shadow paging.
• Delta Merge Process: An asynchronous background process that merges Delta 1 + Main 1 $\rightarrow$ fresh compressed Main 2, resetting the delta memory footprint.

3. Redo Log Characteristics

• WAL log entries contain raw columnar value descriptors, value IDs, and row position IDs.
• Upon system crash, replay populates the Delta Store in RAM up to the last committed LSN.

Row Store Architecture (Pure OLTP)

Tables: NRIV, USR02, System Catalog, Locking
In-Place Segment Model
1. RAM Layout: Linked Page Segments

• Tuples are stored consecutively in 64 KB memory pages linked into table segments.
• Fast primary key pointer lookups and instantaneous single-record writes.
• Memory pages undergo in-place updates with multi-version concurrency control (MVCC) pointers for read consistency.

2. Persistence to `/hana/data`

• Row Engine Converter: Translates Row Store memory page IDs directly into data volume disk blocks.
• Savepoints flush all modified row store pages into shadow blocks on disk. No separate "Delta Merge" step is needed for Row Store.

3. Redo Log Characteristics

• WAL log entries contain physical row images or logical operation records (INSERT tuple values, DELETE record keys).
• Crash restart requires 100% of Row Store tables to be loaded immediately into RAM during startup.

Why is Data Never Lost?

Even though the 5-minute savepoint hasn't run yet, all committed transactions reside in /hana/log. During Phase 2, the Redo Engine reads every log record newer than the last savepoint anchor and reconstructs the exact memory state.

What happens to In-Flight Transactions?

Transactions that were open and never issued a COMMIT before the power failure will have Redo entries replayed in Phase 2, but are immediately identified and discarded in Phase 3 (Undo Phase) to maintain strict consistency.
